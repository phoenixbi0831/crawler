## Phoenix Tsai｜CDP 數據經理 Personal Brand

當多數人還在「報表做完就結案」的時候，我已經在想：「這一筆資料，還能幫業績多做什麼？」  
我是 Phoenix，一個把「數據」當「成長武器」來用的 CDP 數據經理——從 DW/BI 顧問、專案經理，到數據中台與 CDP 的實戰操盤手，我做的從來不是漂亮的 slide，而是能撐住一個品牌成長好幾年的底層架構。

---

## 擅長領域（背後都有故事）

- **CDP 顧客數據管理與數據中台**
  - 很多品牌都有會員資料，但真的「用得動」的其實不多。我的強項，是把「會員、交易、數位軌跡、第三方資料」整成一套能長期運轉的 CDP 與 Data Lake / Data Mart。
  - 從金控到餐飲、從電商到社群商務，我習慣先問一句：「你未來三年要靠數據賺什麼錢？」再往回設計資料架構，而不是只為了現在的報表拼湊資料。
  - 關鍵場景包含：資料規範建立、DW / CDP 維運流程設計、跨系統 API 串接、與 Data Team 的組織與分工規劃。

- **數據分析與模型標籤設計**
  - 我不只會做 RFM、分群、分類、CLV、預測與推薦模型，更在乎的是：行銷或業務看到這些結果，下一步「真的知道該做什麼」。
  - 於是我用「事實標籤 / 模型標籤 / 預測標籤 / 外部標籤」分層設計了一套會員標籤體系，從會員基礎、內容偏好、關聯行為到預測行為，讓每一個標籤都對應到實際應用情境。
  - 工具只是手段：Python、R、Tableau、SSIS/SSAS/SSRS、Informatica、PL/SQL、Smart eVision…我關心的是，這些工具最後能不能說服一個不懂技術的決策者做對的決定。

- **EC & O2O 流程設計與優化**
  - 我見過的餐飲與 EC 流程優化，不是從會議室開始，而是從門市櫃台、外送人員動線與顧客等待的表情開始。
  - 有一個經典案例：從 2012 年的舊外送流程到 2016 年的新外帶流程，我和團隊一起把店長、外送人員、人力配置、出單節點、保溫箱位置全部打掉重練，結果是——顧客等候體感下降、人員混亂度下降，但營運效率上升。
  - 這些調整，背後都有數據在撐：出餐時間分佈、取餐高峰、線上線下訂單比例、SOP 違反率…我喜歡用數據把這些「直覺」變成能被複製的 SOP。

- **專案管理（瀑布＋敏捷）與跨部門協作**
  - 身為專案經理與部門主管超過 10 年，我最在意的從來不是「專案有沒有準時驗收」，而是「上線之後，有沒有人願意用」。
  - 我習慣站在 User 旁邊一起畫流程，用他們聽得懂的語言整理需求，再翻譯成技術規格跟團隊與外包夥伴對焦，確保上線那天大家不是被通知，而是「終於等到」。
  - 不管是傳統瀑布式專案，還是 Scrum 與敏捷導入，我擅長的是讓人、流程與系統在現實限制下找到一個真的走得下去的平衡點。

- **社群商務與人脈互動平台設計**
  - 在社群與人脈場景裡，數據不是冷冰冰的欄位，而是一段段互動關係。我用 SLATES（Search, Links, Authoring, Tags, Extensions, Signals）與 4RC（Recommend, Ranking, Rating, Review, Reply）去拆解這些互動。
  - 在 EMBA 人脈社群平台與社群商務實作裡，我設計了 PCI / CCI / SCI 等互動指標，讓「誰跟誰熟、誰是關鍵節點、誰是潛在影響者」不再只靠感覺，而是有圖、有數字。
  - 這些設計，後來被用在聊天機器人、社群內容經營與人脈拓展上——平台不是只在蒐集點擊，而是在累積「人與人之間的關係資產」。

## 作品集與代表案例（可以放進 Pitch Deck 的那種）

### 1. 模型標籤體系設計（讓「會員 360」真的可以用）

- **標籤架構設計**
  - 很多公司口號喊「會員 360」，但員工打開系統只看到一堆欄位。我做的，是把這些欄位重組成「會員基礎標籤、內容標籤、關聯標籤、行為標籤、預測標籤」五大類。
  - 這五大類，對應到不同 stakeholder 的日常：行銷要看偏好與生命周期、營運要看消費與頻率、客服要看接觸紀錄與問題、決策者要看預測與價值。

- **標籤生成邏輯**
  - 在實作上，我會先把事實標籤（交易、瀏覽、互動）整理乾淨，再疊上模型標籤（分群、等級）、預測標籤（流失、回購、開信、點擊…），必要時加上 DMP 或外部 open data。
  - 最後的目標只有一個：讓行銷企劃在拉名單的時候，不需要再找 IT 幫忙寫 SQL，只要講一句：「我要高價值、近期有互動、但快沉睡的舊會員」，系統就知道要怎麼找人。

### 2. CDP 與 DW 架構規劃與導入（把分散的資料拉成一條線）

- **資料倉儲與 CDP 顧客數據管理**
  - 在金融產業（銀行、人壽、產險），我參與與規劃的 DW / CDP 架構，核心挑戰從來不是技術，而是：這麼多系統（官網、APP、EC、POS、客服、活動、社群、第三方 DMP），到底要怎麼講同一種「客戶語言」？
  - 所以我們先定義唯一的客戶鍵與標準化維度，再設計資料交換節點與分流機制，確保每一個行為都能回流到同一個「顧客故事時間線」上。

- **數據中台與視覺化分析**
  - 我把資料中台想像成「讓前線自己開車的駕駛座」。透過 Data Lake / Data Mart 設計＋ Tableau 等 BI 工具，讓行銷、業務、產品可以自己拉報表、自己看 MoM 變化，而不是每次都開 ticket 給 IT。
  - 對管理層來說，他們看到的是：各管道（自然搜尋、自媒體、廣告、異業合作…）的效益一目了然，預算要砍哪裡、加碼哪裡，都有數據可以撐腰。

### 3. 平台互動關係設計（SLATES ＋ 4RC，讓用戶留下來的理由被看見）

- **社群互動設計**
  - 在 EMBA 社群與社群商務的場景裡，我用 SLATES（Search, Links, Authoring, Tags, Extensions, Signals）與 4RC（Recommend, Ranking, Rating, Review, Reply）去拆解：「一個人為什麼會願意一直回來這個平台？」
  - 從搜尋關鍵字、發文與標籤，到推薦、評價與留言，我把每一個動作都當成一塊可以被量化的「互動磚塊」，最後讓平台可以看見：誰是核心貢獻者、誰是潛在 KOL、哪一類內容真的有用。

- **互動關係模型**
  - PCI（以參與者為中心）、CCI（以內容為中心）、SCI（以同類型為中心）這三種互動關係模型，搭配 Neo4j 等圖形資料庫，讓我們能畫出一張非常直覺的人脈互動地圖。
  - 平台營運的人只要看這張圖，就知道今天要經營哪一群人、推哪一種內容，才有機會把更多被動的成員拉進來變成活躍參與者。

### 4. EC 線上線下整合與服務動線優化（把顧客從「等到不耐煩」拉回來）

- **外送 / 外帶流程重塑**
  - 有一次，我們在門市做現場觀察，看見的是：線上訂餐的客人到店，櫃台沒人理；餐點早就出餐放冷，員工卻忙著處理別的事。這些都沒有出現在任何一張報表裡。
  - 後來我們調整了人力配置（店長＋外送人員一起在櫃台）、把出單時間改為系統控制、重畫取餐動線與保溫箱擺放位置，結果是：顧客抱怨下降、餐點品質提升、現場混亂度明顯降低。

- **線上線下系統整合**
  - 技術面上，我們把 EC 訂餐、POS、Call Center、外送平台與門店營運系統串在一起，讓每一筆訂單從「下單 → 出餐 → 取餐 → 回饋」都有資料可以追蹤。
  - 這些數據再回流 CDP 與 BI 報表，讓營運與行銷不只是「感覺今天比較忙」，而是可以清楚看見：哪個時段爆量、哪個品項成長、哪種活動真的帶動了回購。

### 5. 人脈社群平台與聊天機器人架構（小團隊也能玩的雲端架構）

- **平台系統架構**
  - 這個專案從一開始就知道「預算不會多」，所以我選擇 Heroku、Google Dialogflow、Line Message API、Google Drive API、Python、Neo4j 等雲端與開源技術，拼出一個 CP 值極高的平台架構。
  - 透過模組化設計，平台可以隨著人數與互動量成長而調整資源，讓小團隊也有能力玩出一套真正有數據資產的人脈社群平台。

- **聊天機器人與社群商務**
  - 在這個架構裡，聊天機器人不只是客服工具，而是「資料入口」。每一句對話、每一次點擊、每一個內容互動，最後都會被整理成 SLATES / 4RC 相關的標籤與指標。
  - 對品牌來說，這不只是多了一個對話通路，而是多了一個可以長期累積人脈與商機的資料金礦。
